# 2. Problem and Goals

|Problem|Goals|
|---|---|
| Problem statement (what is wrong today?) | Some of the delivered platforms have common properties and depending on these common properties we want to commonize purchases list for a platform by defining small-commonized ready-to-use purchase lists. But these sub groups may also be given parameters, that may change the properties of the items, so that i can use them with small variations. As an example if a re-usable purchase group has computers, i want to give a parameter to the purchase list definition and it will set the RAM size of the computers found in that purchase list. |
| Business / mission goal | The goal is to provide a tool for the pruchase specialists that he/she can commonize some parts of the different purchase lists and reuse them as a group and spend less time to prepare a final purchase list.  |
| Project objectives (measurable) | Showing a purchase list on the web interface should not exceed  2 seconds. |
| Success criteria / KPIs | All the unit tests, scenario tests should be written with full coverage and should pass, also no clippy error and CPU usage should not pass %1 and memory usage of backend rust service should not pass 50 MB.  |
| Expected benefits | Purchase specialists will gain time by commonizing the purchase lists of platforms.|
| Consequences of not doing the project | Purchase specialists spend more time for platform purchase lists. |

# 3. Scope

| Item | In scope | Out of scope |

### 4.3.4 Notes and Clarifications

1. **Memory measurement:** The 50 MB limit applies to the Rust backend service process, not the entire Docker container. The measurement method (for example, resident set size), test workload, and measurement interval should be defined before verification.
2. **CPU measurement:** The 10% CPU limit should be verified under a documented workload, host configuration, and measurement interval.
3. **Response-time measurement:** The 2-second target should be tested with a documented database size, workload, test environment, and measurement boundary.
4. **Test coverage:** The project should define the coverage metric and the code included in the coverage calculation.
5. **Interface classification:** gRPC and PostgreSQL are internal system interfaces in this architecture. ZIP and CSV define the backup/restore data-format interface.
6. **Budget and schedule:** No budget limit or delivery deadline was specified in the project definition; these constraints remain unspecified.
